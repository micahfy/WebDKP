# 主团 / 替补队长完整数据同步

适用 WoW 1.12、Lua 5.0。A、B 必须同公会并安装支持本协议的 ADKP。网络只使用 GUILD 插件频道；SuperWoW 的 ImportFile / ExportFile 用于独立本地快照。

## 使用

1. A 在「替补 / 设置」设置替补队长 B，勾选「与替补队长同步数据」。网站初始分可以先导入，也可以建立链接后再导入。
2. B 收到显示真实申请人、团队和版本的整库申请。接受后自动绑定 A；新数据接收完整并通过校验才替换 B 的业务数据库。
3. 此后 A 的记分、改分、删除、人员变化及记分设置自动同步。B 的业务副本只读，替补名单功能保留。
4. A 每次重新导入网站初始分，B 都重新接受。B 未接受时保留旧数据；A 可以继续记分，新基准及后续操作排队同步。
5. 登录或入团后通过 GUILD 检查原链接。A 需要恢复时确认真实提供者，先校验本地完整快照，匹配则本地恢复，否则请求全部数据。B 保留有效授权时自动补齐；授权也丢失时需要确认来源。
6. 「检查恢复」可手动查询。A 有本机完整快照但对端未回复时，也可确认从本机恢复；稍后仍会与对端核对。
7. 取消勾选可断开链接。更换替补队长会断开旧链接，需要重新勾选申请。删除正在同步的团队前先断开。

## 同步申请没有弹窗时

A 发起后，状态会区分「对端尚未回复」「替补队长已收到申请，等待其确认」和「对端正在作为主团」。只由 A 勾选发起同步；B 收到申请后点击接受即可，不需要先勾选。若 B 正在向别人发送主团数据，先取消 B 的同步勾选，再由 A 重新申请。

系统弹窗位置被占满、播放过场或者窗口被临时隐藏时，插件保留申请并重新尝试显示，不视为玩家拒绝。点击取消或按 Esc 才拒绝该申请；未确认前不改动业务数据。

A、B 都可输入 `/adkpsync`，查看协议、初始化、公会、插件总开关、角色、同步对象、收发分片数、最近完整消息，以及发送失败的完整错误文字（不受界面状态栏截断）。双方必须更新完整的 `ADKP` 文件夹，并在更新后重新登录或 `/reload`。若收发计数没有增长，先检查公会与插件总开关；若显示收到申请但窗口未出现，保留这段诊断输出供排查。

## 数据与版本

- 每端只维护一个活动链接 / 业务副本。团队标识和重置编号隔离不同主团及不同次网站重置。
- 业务版本为日期 + 当日递增修订号。跨午夜不清数据；同日导入不归零，接收和崩溃恢复不增加版本。
- 全部网站初始分、人员、活动 / 装备 / 替补记录、Boss 自动加分元数据、大小号关系与基准、记分配置均在快照内。不按日志日期过滤。
- 本机窗口位置、主从身份、授权不作为共同业务内容校验；B 的自动组人设置不被 A 覆盖。
- 初始复制先复制网站基准，再顺序接续操作。增量队列保留最近 128 次操作；若增量已缺失，则以当前完整快照补齐，不丢弃当前数据库的历史记录。
- 人名采用每次重置内稳定编号，新增成员追加编号，离团不复用编号。记录携带实际参与人员，不根据接收方实时团队名单重算。

## 可靠性

包长度按字节限制，消息分片、限速、确认、补传及去重。发送包不使用裸竖线 `|`，避免 1.12 客户端的聊天转义校验；字段中的分隔符及物品链接转义传输。保留全局 `SendAddonMessage` 调用链，兼容其他插件的限流计数。网络协议已升级为 `ADKPSYN2`，A、B 必须同时更新 ADKP 并重载；旧网络协议不互通。新版完整快照按团队保存替补/装备历史；没有新版完整结构的旧文件不参与恢复。传输内容使用有复杂度限制的数据编码，不执行收到的 Lua。网络发送者使用 CHAT_MSG_ADDON 的真实 sender，并只接受 GUILD。

内存副本与文件快照状态分开显示。独立文件位于 SuperWoW 的 `imports` 目录，名称为 `ADKP-SYNC-<角色身份校验值>-0/1.txt`。两个槽交替写入并读回校验；不依赖可能随 SavedVariables 丢失的最新备份指针。这是同一数据库的写入保护，不是多团归档。

同步文件检查点采用 `ADKP-SYNC2:` 和可逆压缩编码，每个槽均含完整当前数据库；对端确认完整当前版本后不再保存旧导入基准。未完成首次同步的基准继续保存。此前 `ADKP-SYNC1:` 全量文件仍能读取。数据列表的 D 文件采用 `ADKP-BACKUP3:`，只保存一次当前业务快照；本地与网络共用编码器，文件封装并不等同于网络消息。

数据列表的本地备份已升级为新版全量 D/P 文件，旧 CSV 格式不再参与恢复。登录检查统一选择本地或对端的有效新版本；拒绝后可继续记分，但暂停自动备份和同步发布。详见 [本地备份与登录恢复](LOCAL_BACKUP.md)。

对端离线时未传出的操作依靠本机保存。操作既没有被对端完整确认，也没有成功写入任何本地快照时，无法保证崩溃后找回。

## 传输效率与诊断

完整快照和增量消息在发送前自动选择最短的百分号转义、Base64 或 LZW 压缩 + Base64。压缩使用纯 Lua 5.0、12 位编码和最多 4096 项字典，解压长度有上限；不依赖额外插件。接收方名称保留完整可逆编码，减少每包中文名称的转义开销；仍依据真实发送者和明确接收方校验。

限速保持 500 字节/秒。100 人、无历史记录、精简记分配置的同一模拟样本，接受后数据追平耗时从 21.9 秒降为 9.1 秒，实际双向协议通讯量从 12004 字节降为约 5380 字节。这个结果不是实际公会网络的速度保证，配置、历史、中文姓名长度及丢包会影响耗时。

业务确认超时从完整消息的接收确认后计算，避免长传输刚结束就重新发整库。已有同一轮有效副本时，发现版本落后会请求顺序补齐操作；增量不在队列里才回退完整快照。版本或内容不匹配仍完整校验后替换。

A 输入 `/adkpsync` 可查看累计发送字节、补发分片及最近整库/增量的原始大小、编码后大小、分片数和耗时。编码 `E` 是转义，`B` 是 Base64，`Z` 是压缩 + Base64。这些计数包含插件前缀和包头，不包含底层网络协议开销；“发送耗时”和“业务确认耗时”分别表示分片发出及数据应用被对端确认。

## 验证

从仓库根目录运行：

```text
python tests/run_sync_tests.py --lua <Lua-5.0解释器路径>
```

测试包含真实网站导入、主替加分与 Boss 标记的提交路径、两端通信模拟、丢包、名单变动、跨午夜、重置确认、旧确认失效、双方崩溃、本地及网络完整恢复、文件写入失败、日期倒退、只读界面、长时间的 40 人传输、压缩字典重置/任意字节还原、无效编码拒绝、100 人传输基准和延迟业务确认下不重复发送整库。

仍需在游戏内使用两个同公会角色检查弹窗、中文字体布局、实际 GUILD 收发，以及真实客户端退出 / 崩溃后的文件恢复。
